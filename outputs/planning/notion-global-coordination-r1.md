## 1. 目的、原因与边界

目的：多个项目在 Edward’s Notion 与元见 PrimeViz 之间正常记录、查阅、更新，用户不因项目交替而反复切换共享插件认证、复制记录或维护多套数据。

原因：既有协调机制处理共享连接的占用，但不选择固定工作区；项目已有不同写入合同和凭证路径，独立锁不能自动组成全局互斥。增加单项目连接不能独自解决跨项目统筹。

本轮研究问题：现有模块能复用哪些；如何按项目确定工作区与精确对象；如何协调读取、有限写入和失败恢复；以什么证据结束本轮。采用技术描述、比较与方案判断，结论上限为已验证本地能力与尚未核验的真实接入，不证明真实两区已经运行。

用户已明确：不需要手机 App 数据实时上传 Notion；不要基于日期和时间安排工作。

非目标：手机上传、后台无限任务、服务器、跨机器多写者、搬移/复制旧库、公开分享、扩大成员权限、升级付费计划、读取无关秘密、改写项目真源、改训练处方、部署或 Git 提交。全局协同只统一调用、仲裁与回执，不统一各项目的数据所有权。

## 2. 完成效果与实际场景

以下是目标体验，不是当前上线声明。本地保存、确定性路由和两区替身贯穿已经实现；真实交替录入及本人体验未验收。

1. 在 X-Fit 对话明确要求保存训练反馈，系统按 X-Fit 绑定进入 Edward，保留本人反馈来源；不顺带修改手机或训练偏好。
2. 紧接着在体育组队请求更新已授权工程摘要，系统选择 PrimeViz 的固定连接，用户不重新选 OAuth 工作区。
3. 在 Bene 仓库中指定 Glimmer 或 Showcase，分别读取其业务子项目绑定；只说“Bene”且涉及多个可能目的地时，仅询问这一次归属，不按目录猜写入地点。
4. 两个任务同时提出写入，提交到同一本机执行队列。每批先核验身份、对象、范围和预览；执行完回读再释放。独立事实检查可以并行。
5. 一区未授权或额度受限，该区显示待处理；另一区已具备条件的独立任务仍可推进。不切到另一区代写，不通过换连接规避限制。
6. 创建响应丢失或更新回读失败，显示“结果待核实”，从同一 operation ID 恢复；不让用户重录，不盲重发。
7. 查询进度可看到已保存本地、待同步、冲突、结果待核实、回读通过的区别；“执行过”不等于“同步完成”。

日常用户入口保持 App 与当前对话分工：实际训练仍在 App；项目反馈和已授权协作更新可在对话发起；Notion 是可选查看入口。普通记录请求在已明确的目的地与授权范围内不额外逐条重复确认。正式规则、重大权限、跨区归属变更、新训练计划和手机写入仍各有确认门。

## 4. 推荐结构与确认点

### 4.1 固定路由，不切共享认证

调用链：

`请求 → project/subproject ID → 路由与源版本 → 固定 workspace/channel → 身份及目标核验 → 预览与授权 → 有限执行 → 回读/回执`

路由配置只存非秘密元数据：project/subproject ID、工作区 UUID、channel ID、精确目标、项目 adapter、负责字段、操作能力、绑定来源与版本、验证状态。

凭证按 connection/profile 分开存于 Keychain，不仅按工作区名区分，因为同一区可能有多个 bot/不同范围。两个工作区的固定连接可以并存；保留 X-Fit 专用凭证和私有范围，不强求恰好只用两个 token，不将个人连接扩权为全项目万能凭证。

找不到路由、归属歧义、身份不匹配或对象不在允许范围时，停止相关远端动作。不以当前 UI、标题、UUID前缀或轮流试两区决定目的地。

### 4.2 一本机写入执行器，有限批次

- 首版独立读取可并行；所有采用全局入口的实际写入先全局串行，每批只属于一个项目、一个连接和一个 adapter。
- 共享 connector/native-app 仍各自排队。直接 API、旧同步器和共享路径对同一对象必须经统一准入与仲裁，不能因为各自有锁就同时写。
- 未接入旧任务或人工编辑仍可能绕过入口；版本检查和回读继续必需。采用率不足时报告覆盖不完整，不宣称全系统强制互斥。
- 不按时间过期夺取 lease。崩溃或未决调用先核实际结果，由 owner/人工认可恢复；不强制释放、不切认证抢占。
- 平台 Retry-After 仅是传输安全条件，不是项目排期。读取重试有上限；不确定写结果先核实，不换 token 规避限额。

### 4.3 队列、状态和回执

每项操作包含 project-scoped operation ID、来源定位/指纹、route 版本、目标、adapter 与允许操作、确认范围、预览指纹、实际返回 ID、读回指纹、状态和重开条件。

全局队列只保存必要索引；个人正文留在所属项目受保护记录中，不在全局复制餐食或训练全集。日常反馈先保留本人来源；意见不自动成为已确认规则。

执行状态：`saved_local → pending_route/authorization → preview_ready → executing → readback_verified`；旁路状态为 `conflict / result_unknown / blocked_access / cancelled`。

重复提交相同意图不创建新 operation。同 ID 内容变化、路由变更、人工修改或源变更要求重做预览；不能覆盖旧回执制造一致。读回一致或真实 no_op 才显示同步完成。

### 4.4 需要确认的决策与冲突

| ID | 推荐决定 | 主要取舍/边界 |
|---|---|---|
| D1 | 保留两个固定工作区连接，由项目路由选择 | 一次明确授权，换取日常不切 OAuth；不自动配置或提取共享凭证 |
| D2 | 复用已有同步器，新增薄协调层 | 需核版本与合同，避免重复引擎；不直接改全局旧 skill/AGENTS |
| D3 | 首版本机单写者，独立只读并行 | 吞吐保守，换取更小故障面；未接入客户端不在强制覆盖内 |
| D4 | 权属与操作能力按项目保留 | 统一入口但不统一真源；X-Fit append、足球 owned update 分开 |
| D5 | 全量盘点6候选，真实试点先选两个已确认项目各处一区 | 其余按独立准入逐项推进，不猜 GreenDeagle、Showcase 目的地 |
| D6 | 原 T3 单独续做，框架不替代建库 | 全局底座和 T3 各自验收；父页/创建器缺项不会被测试 PASS 吞掉 |

备选A：继续共享 OAuth 与排队。可以协调占用，但日常仍依赖当前认证，不能满足无切换目标，保留为有限备用。

备选B：每个项目各造独立同步器。可以固定连接，但重复凭证、锁、恢复和回执，不作为推荐新增路径；保留已存在的敏感项目隔离 adapter。

备选C：一套服务器/分布式调度与全自动双向同步。首版维护与授权面过大，暂不做。用户若明确提出多 host 运行，再重新设计。

Global schema/grant 首次需要一次完整确认。具体人工作业区域、私有父页、工作区不明、生产凭证与真实写入范围仍按目标核对；一次框架确认不取代未知项目授权。

## 7. 数据反馈、版本与循环迭代

每次调用：读取所属项目当前事实与绑定→解析依赖与授权→只推进ready→保存操作回执→真实回读→刷新该任务状态。相同项目正文维护一次，Global只存索引/引用。

反馈按三类处理：

- 路由/保存/回读故障：记录具体operation、观察和失败层，先修最小真实层；重复错误不盲重跑业务动作。
- 信息与真源冲突：保留双方和来源，暂停冲突字段，等待owner决定；不得改变基线吞掉冲突。
- 使用体验：记录切换次数、重复录入次数、纠错及是否完成任务；先取真实基线，不编造提升百分比。耗时可作为观察数据，不转为工期承诺。

规则变化采用新版本及确认记录。route/profile变化作废相关旧preview；已完成操作不重做。skill只保存流程与停止条件，个人数据/环境/账号放project adapter和dossier。没有成熟重复证据，不把一轮日志晋升为全局经验。

信息归属沿既有体系：业务流程在项目循环手册；调用方法在运行手册与已安装skill（本轮不改skill）；实际在App/对应项目；确认规则与决策在需求/偏好版本；问题和解决结果在本需求及案例；任务JSON只索引出口/门，操作回执只记录该意图。Notion后续投影这些内容供查看/反馈，不成为另一个自动覆盖App或仓库的真源。

具体循环例：一区身份不符→该意图blocked而不改目的地→按profile核验真实原因→取得新证据→用同一ID重做失效预览→完整回读→复投确认写0。输入体验的循环例：同手机/同任务建立基线→最小修正→同口径复测→本人体验；模拟器PASS不能代替真机P95。框架本身也评估维护负担；若记录成本超过避免的返工，先减字段/合并视图，不自动增库。

迭代触发是新证据、实际失败或用户批准，不是到了某一天。每轮冻结任务集合；新需求进入候选，不为凑数延长本轮。ready为空时，分别交付软件实现、Owner授权、必要数据和真人验收等未满足条件，再停止；不能把Agent缺实现统一归为外部阻碍。下一轮最多三个重点。
