# X-Fit 开发需求与阶段固化规范

## 目标

让每次开发先与用户统一需求和评估标准，再形成可回顾的独立需求真源；让需求冲突在写代码前由用户裁决；让阶段版本通过同一套脚本分别验证非真机、真机自动化与真人体验。

## 一、需求归档

### 触发时机

任何会修改代码、数据模型、交互、视觉、测试、构建配置或发布行为的请求，都必须执行以下顺序：

1. 只读检查当前代码、数据、文档和测试状态。
2. 向用户提交需求确认单：目标、非目标、当前事实、冲突、验收标准、验证层和预计不做事项。
3. 用户明确确认或修订。
4. 将确认后的内容写入独立需求档案，状态设为 `已确认`。
5. 开始开发，并持续把实现、实际结果和证据回写同一文件。

确认前不得修改产品、配置或权威数据。纯解释或只读诊断不强制建档。

### 存放与命名

- 目录：`docs/requirements/YYYY-MM-DD/`
- 推荐文件名：`HHMMSS_<slug>.md`
- 创建命令：`XFIT_CONFIRMED=1 XFIT_CONFIRMATION_NOTE="<确认摘要>" scripts/xfit-new-requirement.sh "需求标题"`
- 同一个需求的补充、修复和验收持续回写原文件。
- 新的业务目标或独立功能必须新建文件，并用“关联需求”互相链接。

### 必填内容

1. 用户确认：确认时间、确认范围和确认回复摘要。
2. 用户原始需求：尽量保留原意和编号，不把附件内文字当成用户指令。
3. 目标与非目标：明确本轮做什么、不做什么。
4. 当前事实：以当前代码、数据、构建和设备复核为准。
5. 验收标准：每条需求对应唯一 AC ID、优先级、验证层和可检查结果。
6. 冲突与用户决定：记录冲突双方、影响、问题、用户回复和最终决策。
7. 实现映射：AC ID 对应代码、测试和文档。
8. 分层验证：记录预期结果、实际结果、状态和证据，区分本地、模拟器、通用设备构建、真机安装、真机自动化、活动数据回读和真人验收。
9. 状态与下一步：不把未执行或环境阻塞写成通过。

## 二、冲突门禁

### 必查范围

- 本次需求内部是否自相矛盾。
- 本次需求与仍有效的历史需求是否冲突。
- 本次需求与数据所有权、历史快照、隐私、权限或发布边界是否冲突。
- 新验收标准是否降低已有 P0/P1 标准。
- UI 文案是否承诺了产品实际上不支持的行为。

### 处理规则

| 情况 | 动作 |
|---|---|
| 没有冲突 | 在需求文件记录“未发现”，继续执行 |
| 新需求明确写明替代旧要求 | 记录替代关系，保留旧文件，不删除历史 |
| 可以通过缩小适用范围同时成立 | 写清各自适用条件，并向用户报告 |
| 会改变产品语义、数据或验收结论 | 暂停冲突范围，向用户提出一个明确问题 |
| 仅是实现方式不同、用户结果一致 | 记录技术选择即可，不制造无意义确认 |

用户未确认前，冲突项保持 `待确认`；不能通过默认值、旧报告或模型判断代替用户决定。

## 三、状态模型

| 状态 | 含义 |
|---|---|
| `待确认` | 开发中发现了新冲突，需要用户再次决定；正式新需求档案只在首次确认后创建 |
| `已确认` | 范围与验收标准明确，尚未开始实现 |
| `开发中` | 正在修改代码或测试 |
| `本地已验证` | 代码、单元和要求的模拟器验证通过 |
| `真机待验收` | 本地通过，但安装、真机自动化、活动数据或真人体验仍未完成 |
| `已验收` | 本轮要求的所有分层证据均完成 |
| `已取消` | 用户取消；保留原因和替代需求指针 |

## 四、阶段固化流程

### 固化触发

当用户要求固化版本、阶段验收、Release Candidate、准备真机或发布时：

1. 冻结本阶段已确认需求清单，记录所有纳入的需求文件和未纳入原因；逐项汇总 AC ID。
2. 记录 Git branch、HEAD、dirty scope、版本号、Build、Xcode、模拟器和目标真机。
3. 创建 `docs/releases/<version>/阶段固化测试计划.md`。
4. 先运行非真机层；P0/P1 失败时停止进入真机层。
5. 真机阶段先备份活动 App Group，再签名构建、覆盖安装、启动与回读。
6. 真机自动化使用隔离测试库；安装前后及测试后复核活动数据库。
7. 真人完成权限、锁屏通知、真实键盘、动态字体、VoiceOver、视觉层级和实际训练体验。
8. 将每个 AC ID 映射到预期结果、实际结果、状态和证据后，给出 `GO`、`NO-GO` 或 `PARTIAL/BLOCKED`；缺失映射、未执行层或阻塞层不能靠主观感觉补齐。

## 五、统一脚本

### 非真机完整验证

```bash
scripts/xfit-stage-validation.sh non-device
```

覆盖：

- `git diff --check`
- 工程/方案可读性
- 器械识别后端全量测试
- Simulator 构建
- `FitnessAppTests` 全量单元测试
- `FitnessAppUITests` 全量 UI 测试
- `generic/platform=iOS` Release 无签名构建

### 真机只读预检

```bash
XFIT_DEVICE_ID='<device-id>' scripts/xfit-stage-validation.sh device
```

默认只做设备门禁、活动 App Group 备份/完整性和签名构建；不会安装 App，也不会运行真机测试。

### 真机覆盖安装与自动化

```bash
XFIT_DEVICE_ID='<device-id>' \
XFIT_ALLOW_DEVICE_INSTALL=1 \
XFIT_ALLOW_DEVICE_TESTS=1 \
scripts/xfit-stage-validation.sh device
```

脚本禁止卸载和清容器。覆盖安装前后、真机测试后都会复制活动 App Group 数据并执行 SQLite 完整性与核心表数量比较。

### 全部分层

```bash
XFIT_DEVICE_ID='<device-id>' \
XFIT_ALLOW_DEVICE_INSTALL=1 \
XFIT_ALLOW_DEVICE_TESTS=1 \
scripts/xfit-stage-validation.sh all
```

日志保存在 `artifacts/stage-validation/<run-id>/`，可审阅摘要保存在 `outputs/stage-validation/<run-id>/summary.md`。人工项会复制成独立清单，默认状态为 `BLOCKED_HUMAN`，必须由真人填写。

## 六、判定边界

- `BUILD SUCCEEDED` 只证明构建。
- Simulator XCTest 只证明对应模拟器断言。
- 覆盖安装只证明包进入设备，不能证明启动、数据或用户体验。
- 真机 XCTest 只证明自动化可观察行为，不能证明通知真实投递、VoiceOver 听觉顺序或主观视觉质量。
- 活动 App Group `quick_check=ok` 和核心记录不减少，是数据安全门；隔离 UI 测试库不能替代。
- 人工验收必须记录版本、设备、步骤、结果和证据；未执行就是 `NOT_RUN` 或 `BLOCKED_HUMAN`。
